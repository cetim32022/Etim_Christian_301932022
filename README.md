## Case study — Lagos Heritage Pensions Ltd

**Lagos Heritage Pensions Ltd** is a fictional Nigerian Pension Fund Administrator (PFA) operating under the Contributory Pension Scheme (CPS). It manages:

* **Employers** — Nigerian employers who remit monthly contributions on behalf of their staff.
* **Employees / RSA holders** — individual savers, each with one Retirement Savings Account.
* **RSA accounts** — the savings account itself, with a balance, a status, and an assigned pension fund.
* **Pension funds** — RSA Fund I, II, III and IV, the four PenCom-defined risk-banded funds.
* **Fund unit prices** — daily unit price per fund (used to convert naira contributions into fund units).
* **Pension Fund Custodians (PFCs)** — the licensed institutions that actually hold the cash before it is invested.
* **Contributions** — monthly employer + employee lines. Employer share is 10 % of salary, employee share is 8 % of salary (PenCom statutory minimums).
* **Withdrawal claims** — retirement, early, involuntary and death benefits paid out of an RSA.
* **Fund switches** — a member moving their balance from one RSA Fund to another.
* **Beneficiaries** — nominees of an RSA holder, whose shares per RSA must total ≤ 100 %.

All names, cities, states, employers and amounts are Nigerian. Naira amounts use the ₦ formatting only in prose; the database stores plain `NUMERIC` columns.

This portfolio **does not** model wallet transfers, card payments or a payment gateway — those are covered by other students' projects.

### Users

| User | What they do with the system |
|---|---|
| RSA holder (member) | Logs into the member portal, views their RSA balance and contribution history, submits withdrawal claims, switches funds, updates beneficiaries |
| Employer HR / finance officer | Uploads the monthly contribution schedule for their staff and tracks remittance |
| PFA back-office operator | Approves / rejects withdrawal claims, posts manual adjustments, runs compliance reports |
| PFA investment analyst | Tracks fund unit prices and balances per fund |
| PenCom examiner (read-only) | Audits contribution and claim history against statutory minimums |
| Custodian operator | Confirms cash receipt from employer before units are credited |

### Data

The biggest table is `contribution` — monthly lines for every RSA holder. In production this is multi-million-row; in this portfolio it is ~60,000 rows generated by `generate_series` inside SQL so the whole portfolio runs in seconds on a Codespaces box. All dates in the seed and bulk files are **relative to `CURRENT_DATE`** so the data never goes stale.

### Operations

The portfolio covers, in order:

1. **Schema design** (P1) — 10 tables in 3NF with PK / FK / UNIQUE / CHECK / partial UNIQUE index / 5 triggers enforcing statutory minimums, withdrawal-vs-balance, retirement age, ledger-driven balances and beneficiary share totals.
2. **Query optimisation** (P2) — 8 reporting queries (4 selective, 4 full-table aggregates) with EXPLAIN ANALYZE before/after adding the selective indexes.
3. **Transactions and concurrency** (P3) — committed / rolled-back / SAVEPOINT-recovery transaction demos in SQL, plus six Python concurrency demos covering lost-update bug, CHECK fix, atomic conditional UPDATE fix (the chosen P3 fix), SERIALIZABLE, READ COMMITTED vs REPEATABLE READ, and a deadlock + fixed-order version.
4. **NoSQL** (P4) — MongoDB 7+ collections for flexible KYC / claim documents (`member_documents`) and portal activity logs (`portal_activity`), with `$jsonSchema` validators, three aggregation pipelines, and a 40 k-document bulk insert + COLLSCAN-vs-IXSCAN demo.
5. **Distributed / cloud** (P5) — monthly RANGE partitioning of `contribution` plus a managed-database design note (multi-AZ, sync vs async, NDPA 2023, PenCom).

## Run order

PostgreSQL (P1 → P2 → P3 → P5):

```
psql -d pensions -v ON_ERROR_STOP=1 -f portfolio-1-database-design/01_schema.sql
psql -d pensions -v ON_ERROR_STOP=1 -f portfolio-1-database-design/02_indexes.sql
psql -d pensions -v ON_ERROR_STOP=1 -f portfolio-1-database-design/03_seed_data.sql
psql -d pensions -v ON_ERROR_STOP=1 -f portfolio-1-database-design/04_bulk_data.sql
psql -d pensions -v ON_ERROR_STOP=1 -f portfolio-1-database-design/05_constraint_tests.sql
psql -d pensions -v ON_ERROR_STOP=1 -f portfolio-2-query-optimisation/01_queries.sql
psql -d pensions -v ON_ERROR_STOP=1 -f portfolio-2-query-optimisation/02_explain_analyze.sql
psql -d pensions -v ON_ERROR_STOP=1 -f portfolio-3-transactions-concurrency/01_transactions.sql
python3 portfolio-3-transactions-concurrency/race_demos.py    # needs psycopg2-binary
psql -d pensions -v ON_ERROR_STOP=1 -f portfolio-5-distributed-cloud/01_partitioning.sql
```

MongoDB (P4, independent of the PostgreSQL run order):

```
mongosh pensions portfolio-4-nosql/01_setup.js
mongosh pensions portfolio-4-nosql/02_data_and_queries.js
mongosh pensions portfolio-4-nosql/03_bulk_and_index_demo.js
```

One-shot runner (Codespaces): `bash setup.sh` once, then `bash runall.sh` runs P1 to P5 in order, commits after each portfolio and finishes with `bash collect_results.sh`, which writes `my_results.txt` from the real logs. The P5 replica is built by `02_replica_setup.sh` and checked by `03_replica_tests.sql`.
